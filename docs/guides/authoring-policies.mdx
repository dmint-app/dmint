# Authoring Security Policies

Dmint provides command-line wizards to translate natural-language access requirements into verified, schema-compliant `policy.json` and `mcp_protection.json` files.

---

## 1. Authoring for Custom Tools (`dmint create-policy`)

When protecting internal functions or APIs, draft your security requirements in a text file named `access.md`:

```markdown title="access.md"
# Database Access Security Requirements

- The agent is permitted to run SELECT queries on any table.
- Inserting or updating records in the 'users' table requires explicit human approval.
- Dropping tables or executing administrative schema changes is strictly denied.
```

Compile `access.md` into `policy.json`:

```bash
dmint create-policy -f access.md -o policy.json -y
```

### Supported Providers and Models

You can specify the LLM provider via `--provider`:

| Provider | Option | Environment Variable | Default Model |
|---|---|---|---|
| **OpenAI** | `--provider openai` | `OPENAI_API_KEY` | `gpt-4o-mini` |
| **Gemini** | `--provider gemini` | `GEMINI_API_KEY` | `gemini-1.5-flash` |
| **Groq** | `--provider groq` | `GROQ_API_KEY` | `llama-3.1-70b-versatile` |
| **Custom / Ollama** | `--base-url http://localhost:11434/v1` | `--api-key <KEY>` | Provider-specific |

## 2. Authoring for MCP Servers (`dmint create-mcp-policy`)

For Model Context Protocol servers (stdio or streamable HTTP), `dmint create-mcp-policy` connects to the server, queries `tools/list`, and generates both the runtime policy and the gateway configuration:

```bash
dmint create-mcp-policy \
  --command npx \
  --args "-y @modelcontextprotocol/server-postgres postgresql://localhost/mydb" \
  --integration-id postgres \
  -f access.md \
  -o policy.json \
  --config-output mcp_protection.json \
  --non-interactive -y
```

## 3. Offline Policy Verification (`dmint verify-policy`)

Before deploying any generated policy to production, validate it offline. This step is **completely deterministic and makes zero LLM calls**:

```bash
dmint verify-policy policy.json
```

Output:
```text
✓ Verified policy.json: 3 rule(s)
  [ALLOW] tool='database', action='select', resource='*'
  [APPROVAL_REQUIRED] tool='database', action='update', resource='users'
  [DENY] tool='database', action='drop', resource='*'
```

### Checks Performed by `verify-policy`
- Schema compliance against the official Dmint specification.
- Validation that rule effects are lowercase `allow`, `approval_required`, or `deny`.
- Verification that no constraints are attached to `DENY` rules.
- ReDoS budget limits on regex patterns (max 256 chars, repetition bound).
- Resource string syntax validation.

---

## 4. Policy Digest Pinning (`dmint policy-digest`)

Calculate the SHA-256 digest of your policy file for runtime pinning:

```bash
dmint policy-digest policy.json
```

Output:
```text
6a8b75f28c19a4e3...
```

Export this value as `DMINT_EXPECTED_POLICY_DIGEST` in your deployment environment. If the file is altered on disk, Dmint will refuse to initialize.
