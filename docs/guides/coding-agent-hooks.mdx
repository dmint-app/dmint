# Protecting Coding-Agent Hooks (`dmint hook`)

Modern AI coding agents execute their highest-impact operations—such as `Bash` / `run_commands`, file edits (`Write`, `Edit`, `apply_patch`, `pre_write_code`), file reads (`Read`, `read_files`, `pre_read_code`), and subagent delegation—through **built-in native tools** in addition to external MCP servers.

`dmint hook` places Dmint's deterministic policy evaluator and single-use Ed25519 human approval engine directly into the official pre-execution hook lifecycle of each coding harness, provisioning a **dedicated policy file per harness** (`.dmint/policies/<harness>.policy.json`) tailored to that harness's complete built-in tool inventory.

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                    AI Coding Harness (Local / Container)                │
│  (Claude Code · OpenAI Codex CLI · OpenCode · Cursor · Windsurf · Cline)│
└───────────────────────────────────┬─────────────────────────────────────┘
                                    │
                                    │ 1. Official Pre-Tool Hook Event
                                    ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                          dmint hook run                                 │
│  • Unpacks harness-specific envelope & de-stringifies JSON params       │
│  • Inspects all batch items (multi-file apply_patch / run_commands)     │
│  • Evaluates .dmint/policies/<harness>.policy.json (native + canonical) │
│  • Enforces strict precedence: DENY > APPROVAL_REQUIRED > ALLOW         │
└───────────┬───────────────────────┼───────────────────────┬─────────────┘
            │                       │                       │
            ▼                       ▼                       ▼
        [ ALLOW ]          [ APPROVAL_REQUIRED ]        [ DENY ]
            │                       │                       │
     Exit 0 ("allow")        Persists PENDING apr_...   Exit 2 ("deny")
     Tool executes           or consumes APPROVED       Tool blocked
                             assertion once
```

## 1. Supported Harnesses, Official Hook Files & Dedicated Policies

Run `dmint init --harness all` (or `dmint hook install --harness <name>`) to configure any or all supported harnesses. Each harness is wired to its own dedicated policy file in `.dmint/policies/<harness>.policy.json`:

| Harness | Flag Value | Generated Hook Configuration File(s) | Dedicated Policy File | Official Hook Mechanism & Output Schema |

## 3. Multi-Resource & Batch Smuggling Protection

Several harnesses allow an agent to batch multiple file edits or shell commands inside a single tool call:
- **Unified Patches (`apply_patch`)**: Codex CLI, OpenCode (`output.args.patchText`), and Cline embed multiple file headers (`*** Add File: ...`, `*** Update File: ...`, `*** Delete File: ...`, `*** Move to: ...`) in one patch body.
- **Batch File Reads (`read_files`)**: Cline accepts `{"files": [{"path": "src/app.py"}, {"path": ".env"}]}`.
- **Batch Commands (`run_commands`)**: Cline accepts `{"commands": ["git status", "rm -rf /"]}`.

`dmint hook run` extracts **every** target file path or command in the batch, evaluates each against the harness's dedicated policy (checking both the native tool name and the normalized capability), and enforces the strictest decision (**`DENY` > `APPROVAL_REQUIRED` > `ALLOW`**). A denied file or command cannot be smuggled inside an otherwise benign batch call.

## 4. Single-Use Human Approvals in Hooks

When a coding agent calls a tool that matches an `approval_required` rule (for example, `git push origin main` or editing `src/main.py`):

1. **First Call Pauses**:
   - `dmint hook run` creates a tamper-evident `PENDING` record (`apr_...`) in `.dmint/approvals.sqlite3`.
   - If Slack, Discord, or Microsoft Teams webhooks are configured (`DMINT_SLACK_WEBHOOK_URL`, etc.), a real-time alert is dispatched.
   - The hook outputs a clear message telling the user/agent how to approve:
     ```text
     Dmint APPROVAL_REQUIRED [apr_8k9P...]: shell.execute on 'git push origin main' requires human sign-off.
     To approve, run: `dmint approve apr_8k9P...` (or use `dmint dashboard`), then retry.
     ```
2. **Human Approves**:
   ```bash
   dmint approve apr_8k9P... --by alice@company.com
   ```
3. **Agent Retries the Exact Tool Call**:
   - When the agent re-runs `git push origin main`, `dmint hook run` computes the RFC 8785 request fingerprint, finds the matching `APPROVED` assertion in `.dmint/approvals.sqlite3`, verifies the Ed25519 signature, atomically transitions the record from `APPROVED` $\to$ `CONSUMED`, and returns `ALLOW`.
   - **Tamper Resistance**: If the agent alters the command to `git push origin main --force`, the fingerprint does not match `apr_8k9P...` and execution is blocked.
   - **Replay Protection**: If the agent tries to run `git push origin main` a second time, the consumed assertion cannot be reused.

## 5. Shadow Mode (Dry-Run Rollout) & Policy Learning

Adopting a policy across an existing repository is safer as a three-phase rollout: observe, review, then enforce. Shadow mode evaluates every hook event and writes the decision to `.dmint/audit.jsonl`, but never blocks the tool call. Use it to discover the real tool and resource surface of a harness before turning on enforcement.

### Phase 1: Observe with shadow mode

Set `DMINT_MODE=shadow` in the environment used by the hook process, or pass `--mode shadow` when invoking `dmint hook run` directly:

```bash
export DMINT_MODE=shadow
# The harness continues to call `dmint hook run`; decisions are logged, not enforced.
```

For a manual invocation:

```bash
dmint hook run --harness claude-code --mode shadow < payload.json
```

`dmint hook run` still resolves symlinks, expands batch patches and commands, and evaluates the dedicated harness policy. The difference is that would-be `DENY` and `APPROVAL_REQUIRED` outcomes are recorded with `shadow_would_block: true` and the hook allows the call to proceed.

### Phase 2: Review what would have been blocked

```bash
# Show shadow-mode entries that would have been DENIED:
dmint logs --mode shadow --search DMT_POLICY_DENIED

# Show shadow-mode entries that would have required approval:
dmint logs --mode shadow --search DMT_APPROVAL_REQUIRED

# Show decision, level, shadow-block count, and top-blocked-resource breakdown:
dmint logs --mode shadow --stats

# Cryptographically verify the SHA-256 audit chain:
dmint logs --verify
```

### Phase 3: Learn and verify a least-privilege policy

`dmint learn-policy` reads the observed audit events and emits a starter policy. Safe read-only operations become scoped `ALLOW` rules, mutating operations become `APPROVAL_REQUIRED`, and destructive commands or secret paths are never learned as `ALLOW` (they are emitted as explicit `DENY` rules).

```bash
# Synthesize a candidate policy without touching the active policy.json:
dmint learn-policy --from-logs .dmint/audit.jsonl -o policy.learned.json

# Review the diff, then verify the candidate offline:
diff -u policy.json policy.learned.json
dmint verify-policy policy.learned.json
dmint check -p policy.learned.json -t shell.execute -r "git status"
```

After review, replace `policy.json` (or the harness-specific policy under `.dmint/policies/`) and switch back to enforcement by unsetting `DMINT_MODE` or setting it to `enforce`.
