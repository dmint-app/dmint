# Docs framework adapters

The templates use generic components. This file says how to express them in each docs framework, and how to detect which one the project uses.

## Contents

- Learning an unfamiliar framework from existing pages
- Component mapping table

- Plain Markdown fallback
- Navigation files

## Detect the framework

`scripts/inventory.py` reports a `docs_framework` guess. Confirm by looking at the docs folder:

| Signal | Framework |
| ------ | --------- |
| `docs.json` or `mint.json`, `.mdx` pages | Mintlify, or a Mintlify-compatible engine (some newer engines read `docs.json` too) |
| `source.config.ts`, `content/docs/**/meta.json`, `fumadocs-*` in package.json | Fumadocs (what better-auth uses) |
| `docusaurus.config.(js|ts)`, `sidebars.(js|ts)` | Docusaurus |
| `_meta.js` / `_meta.json`, `nextra` in package.json | Nextra |
| `.vitepress/config.*` | VitePress |
| `mkdocs.yml` | MkDocs (often Material) |
| `astro.config.*` with `@astrojs/starlight` | Starlight |
| none of the above | plain Markdown (see fallback) |

When several signals appear, trust the one that has the most existing pages built on it.

## Learning an unfamiliar framework from existing pages

If the project already has docs, or the framework is not in this file, do not guess component names. Open the navigation file and two or three existing pages, and write down:

1. Frontmatter keys in use (`title`, `description`, `icon`, `sidebarTitle`...).
2. Which components appear (grep for `<[A-Z]` in the pages) and their props.
3. How code block titles are written (` ```python title="x.py" `, ` ```python [x.py] `, or a comment).
4. How callouts are written.
5. Whether tabs are components or fenced groups.
6. How internal links look (root-relative `/docs/x`, relative `./x`, or with extension).

Then copy those patterns. If you are unsure that a component exists, use plain Markdown instead; a plain table or blockquote renders everywhere, while an unknown component breaks the build.

Useful one-liners:

```bash
grep -rhoE '<[A-Z][A-Za-z]+' <docs-dir> | sort | uniq -c | sort -rn
grep -rhE '^```[a-z]+ ' <docs-dir> | sort | uniq -c | sort -rn | head
```

## Component mapping table

| Need | Mintlify-style | Fumadocs | Docusaurus | VitePress | MkDocs Material |
| ---- | -------------- | -------- | ---------- | --------- | --------------- |
| Steps | `<Steps><Step title="">` | `<Steps><Step>` with `### headings` | numbered headings | numbered headings | numbered list |
| Tabs | `<Tabs><Tab title="">` | `<Tabs items={[..]}><Tab value="">` | `<Tabs><TabItem value label>` | `::: code-group` | `=== "Tab"` |
| Code group (package managers) | `<CodeGroup>` | `<Tabs groupId="pm">` | `<Tabs groupId>` | `::: code-group` | `=== "npm"` |
| Code title | ` ```ts title="auth.ts" ` | ` ```ts title="auth.ts" ` | ` ```ts title="auth.ts" ` | ` ```ts [auth.ts] ` | ` ```ts title="auth.ts" ` |
| Highlight line | `// [!code highlight]` or `{2}` | `// [!code highlight]` | `// highlight-next-line` | `// [!code highlight]` | `hl_lines="2"` |
| Note | `<Note>` | `<Callout>` | `:::note` | `::: info` | `!!! note` |
| Tip | `<Tip>` | `<Callout type="info">` | `:::tip` | `::: tip` | `!!! tip` |
| Warning | `<Warning>` | `<Callout type="warn">` | `:::warning` | `::: warning` | `!!! warning` |
| Cards | `<Card title href>` / `<CardGroup>` | `<Cards><Card>` | custom or `DocCardList` | none (use list) | `grid cards` |
| Mermaid | ` ```mermaid ` | needs plugin | needs plugin | plugin | ` ```mermaid ` |

Treat the table as a hint, and confirm against existing pages and the framework's current docs before relying on a row. Component names and props change between versions.

## Per-framework notes

**Mintlify and Mintlify-compatible engines (`docs.json`)**
- Navigation lives in `docs.json` under `navigation` (groups with `pages` arrays of path strings without extension). Add every new page there.
- Pages are `.mdx` with frontmatter `title` and `description`. An `icon` and `sidebarTitle` are optional.
- Check whether the engine supports every component before using it; read an existing page first.
- An `llms.txt` is generated by Mintlify itself on hosted sites; if the project's engine does not do that, use `scripts/build_llms_txt.py`.

**Fumadocs (better-auth's stack)**
- Content in `content/docs/**.mdx` with `meta.json` per folder for ordering (`{"title": "Concepts", "pages": ["a", "b"]}`).
- Tabs for package managers are a common pattern: a `groupId` keeps the choice in sync across the site. Reuse the project's existing pattern.
- Code block titles and `// [!code highlight]` annotations are supported by the Shiki transformers.

**Docusaurus**
- Sidebar in `sidebars.js`; pages in `docs/` as `.md` or `.mdx`. Admonitions use `:::tip` blocks. Tabs need `import Tabs from '@theme/Tabs'; import TabItem from '@theme/TabItem';` at the top of the file.

**Nextra**
- Navigation via `_meta.js` (or `.json`) files per folder. Callout and Tabs components are imported from `nextra/components`.

**VitePress**
- Sidebar in `.vitepress/config.*`. Code groups use `::: code-group` fences and containers use `::: tip`.

**MkDocs**
- Navigation in `mkdocs.yml` under `nav`. Tabs and admonitions need the matching Material extensions enabled in `markdown_extensions`; check before using.

**Starlight**
- Sidebar in `astro.config.*`. Use `<Tabs>`, `<TabItem>`, `<Steps>` and `<Card>` imported from `@astrojs/starlight/components`, and asides via `:::note`.

## Plain Markdown fallback

Use this when there is no docs framework or you are unsure what renders. It works on GitHub and every static-site generator:

- Steps: numbered headings (`### 1. Install`).
- Tabs: a heading per variant (`#### npm`, `#### pnpm`) with a code block under each, or a table of commands.
- Code title: a bold line above the block, for example **`app.py`**.
- Callouts: GitHub-style alerts, `> [!NOTE]`, `> [!TIP]`, `> [!WARNING]`.
- Diagrams: Mermaid fences (GitHub renders them) or ASCII.

If the project later adopts a framework, these convert with a find-and-replace pass.

## Navigation files

Whatever the framework, after writing pages:

1. Add every page to the navigation file, in the order from the docs plan.
2. Remove entries for deleted pages.
3. Run the checker; it flags pages that exist on disk but are missing from the navigation, and navigation entries that point to nothing.
